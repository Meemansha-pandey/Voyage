## Project Overview

Voyage lets users sign up, describe a trip they want to take, and receive a fully structured day-by-day itinerary, budget estimate, hotel suggestions, and a personalized packing list — all generated by an LLM agent. Users can then modify the itinerary dynamically (add/remove activities, regenerate individual days).

---

## Tech Stack

| Layer | Choice | Justification |
|-------|--------|---------------|
| Frontend | Next.js 14 (App Router) + Tailwind CSS | React Server Components reduce client bundle; App Router colocation of layouts and pages keeps code readable |
| Backend | Node.js + Express | Lightweight, well-understood, strong middleware ecosystem |
| Database | MongoDB via Mongoose | Document model maps naturally to the `Trip` object shape (nested itinerary days, budget, hotels) |
| AI | Anthropic Claude Sonnet | Best-in-class instruction following for structured JSON output; low hallucination on travel data |
| Auth | JWT (jsonwebtoken) + bcryptjs | Stateless, works across deployed API + frontend on separate domains |
| State | Zustand (client) | Minimal boilerplate vs Redux; perfect for auth + trip state |

## Authentication & Authorization

- **Registration**: password hashed with bcrypt (cost factor 12) before persistence. Email uniqueness enforced at DB level.
- **Login**: credentials verified via `user.comparePassword()`. On success, a signed JWT (HS256, 7-day expiry) is returned.
- **Request auth**: `Authorization: Bearer <token>` header required on all protected routes. The `protect` middleware verifies the token, fetches the user from DB, and attaches to `req.user`.
- **Data isolation**: every Trip query includes `{ user: req.user._id }` as a filter. A user requesting another user's trip ID gets a 404, not a 403 — no information leakage.

## AI Agent Design

The AI layer (`ai.controller.js`) wraps three task-specific prompts:

| Endpoint | Input | Output |
|----------|-------|--------|
| `POST /ai/generate` | destination, days, budget, interests | Full itinerary JSON + budget + hotels |
| `POST /ai/regen-day` | destination, day number, preferences | Array of 3 fresh activities |
| `POST /ai/packing-list` | trip details | Categorised packing list JSON |
| `POST /ai/recommendations` | previous destinations, preferences | 3 AI-curated destination picks |

**Prompt strategy**: Each prompt uses a tight system message that demands _only_ JSON output with an explicit schema, plus a clear user message with all relevant context. This dramatically reduces the chance of freeform text polluting the response. Responses are stripped of any accidental markdown fences before JSON parsing, with a try/catch that surfaces a clean error.

## Creative Feature: Smart Packing List + Destination Recommendations

**What it is**: After an itinerary is generated, users can request a personalized packing list tailored to their specific destination, duration, budget, and interests. A separate "Smart Picks" page uses the user's trip history to recommend destinations they haven't been to.

**Why I built it**: The core itinerary/budget loop solves trip planning — but users still face the friction of "what do I actually bring?" and "where should I go next?". Both are personalisation problems the LLM is well-positioned to solve with the context already available in the session, and neither requires any additional user input beyond what was already collected.

**Engineering judgment**: Both features reuse the same AI controller pattern, keeping the abstraction consistent. The packing list is stored back on the `Trip` document so it persists across sessions.

## Key Design Decisions & Trade-offs

| Decision | Rationale | Trade-off |
|----------|-----------|-----------|
| LLM JSON prompting (no tool use/function calling) | Simpler setup; works with any model | Slightly less reliable schema adherence vs native tool use; mitigated by strict system prompt + parse fallback |
| JWT (stateless) vs sessions | No server-side session store needed; works across Vercel + Railway | Token revocation requires short expiry or a blocklist |
| MongoDB document model | Trip object nests naturally; no joins | Harder to query across trips (e.g. "all activities in Paris") if needed later |
| Rate limiting on `/api/ai/` (10 req/min) | Prevents abuse of expensive LLM API | Legitimate power users may hit this; configurable |
| Zustand over Redux | Dramatically less boilerplate | Less tooling for time-travel debugging |

## Known Limitations

- No streaming: itinerary generation is a single round-trip (~3–6s). Streaming responses via SSE would improve perceived performance.
- No email verification on registration.
- Packing list not automatically updated if itinerary is modified post-generation.
- Smart Recommendations page uses a fixed seed of destinations in the frontend demo; the backend endpoint is fully implemented.
